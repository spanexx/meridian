MERIDIAN API ENDPOINTS PER PAGE
A page by page list of every API endpoint each wireframe page needs to load, render, and link to.

Conventions used throughout, taken from docs/apis/00-api-conventions.md:

Base URL on production: https://api.meridian.com/api/v1
WebSocket on production: wss://api.meridian.com/ws
Auth header on every authenticated request:  Authorization Bearer access_token
Mutating requests carry a header:  X-Idempotency-Key operation user timestamp
All responses follow the envelope:  success data or error plus meta with request_id and timestamp
List endpoints accept the standard pagination and filtering query params from 00: page limit sort order plus per endpoint filters
Money values are strings with two decimals: 5000.00
Dates are ISO 8601: 2026 03 13T10:00:00Z
IDs are strings with type prefixes: mem opp exec pay vote tx ev dep wd wm notif gov pool

Status of the API docs:
docs/apis/ contains the conventions plus 01 auth 03 capital 04 opportunity and members.
The other six API docs listed in docs/00 system overview (02 member 05 execution 06 payout 07 reputation 08 marketplace 09 admin) are not yet written.
Where this file names an endpoint that has no doc yet, the path and shape follow the existing convention exactly so the entry is the spec the doc will need to match. These are clearly labeled TBD each time they appear.

IDs in this file use the doc convention when the doc already names them (mem_ opp_ exec_) and the wireframe's wireframe IDs (O-2049, E-1042) are sometimes shown alongside to make the link to what the user sees on screen explicit.


1  LANDING  at wireframe/meridian/landing/index.html

Connection to previous page. None. This is the public entry point.

Endpoints used to load this page.

GET /api/v1/capital/pool/status
  No auth. Public.
  Returns totals total_capital available_capital deployed_capital health reserve_ratio deployment_ratio activity active_executions contributors_count performance avg_roi_30d total_profit_30d executions_completed_30d snapshot_at.
  The landing reads totals to render pool capital 1.42M members 124 and the four numbers in the hero stat strip. It reads performance to render the YTD ROI chip.

GET /api/v1/executions?status=active limit 6
  No auth. Public. Recent ones already shown in the ticker.
  The landing renders the live ticker of in flight opportunities by reading recent executions and their referenced opportunity title and progress.

GET /api/v1/opportunities?status=approved limit 8
  No auth. Public. The ticker also surfaces approved signals that are about to execute.

GET /api/v1/capital/pool/history?period=30d and period=90d and period=1y
  No auth. Public.
  Powers the landing numbers section pool capital sparkline and avg execution ROI sparkline. Three pre shaped SVG paths are already in the page; this endpoint returns the numeric series.

GET /api/v1/testimonials
  TBD. Not yet documented. Used by the testimonials section. Returns a list of member quotes, name, role badges, avatar gradient. Public.

Endpoints exposed from this page. The landing does not own resources. It sends the user to:
  POST /api/v1/auth/register for join the community
  POST /api/v1/auth/login for sign in
  GET /api/v1/opportunities and GET /api/v1/executions for view live opportunities

WebSocket channels subscribed.
  wss://api.meridian.com/ws
  subscribe to channel pool. The page re renders pool capital and the ticker when a message of type EVENT with channel pool arrives. The terminal card on the right is fed entirely from the pool channel playback.


2  REGISTER  at wireframe/meridian/register/index.html

Connection to previous page. From landing via join the community.

Endpoint used on this page.

POST /api/v1/auth/register
  Request body: email, password, password_confirm, terms_accepted true.
  Response 201: member_id, email, status PENDING, message verification email sent.
  Side effects per the existing auth doc: creates member at PENDING, creates zero balance capital account, creates zero reputation record, sends verification email, logs member.registered.

Connection forward. The page redirects to dashboard. That move requires a successful login (which is not yet performed) so register should also implicitly log the member in on success. Per the existing auth doc the cleanest path is to issue tokens immediately on register completion by chaining to verify email or by issuing tokens after register when email_verified_at is set. See follow up notes at the bottom of this file for the resolved token question.


3  LOGIN  at wireframe/meridian/login/index.html

Connection to previous page. From landing via sign in or anywhere session has expired.

Endpoints used on this page.

POST /api/v1/auth/login
  Request body: email, password.
  Response 200 with tokens and member plus requires_2fa false; or response with requires_2fa true and temp_token.
  Side effects: updates last_login_at, creates session, logs member.login.

POST /api/v1/auth/login/2fa
  Used only when login returns requires_2fa true. Request: temp_token, code. Returns access and refresh tokens.

POST /api/v1/auth/forgot-password
  Triggered by the forgot password button. Request body: email. Returns 200 message whether or not the email exists for security.

WebSocket channels subscribed on success.
  wss://api.meridian.com/ws subscribe to channel member self where self is the member_id from the login response. This is the channel from 00 api conventions that delivers member notifications and is the basis for the bell badge.

Connection forward. Tokens stored locally and the page redirects to dashboard.

Two open implementation questions to resolve in the docs before the wireframe becomes implementation ready:

First, registration should issue tokens immediately on success because the wireframe redirects to dashboard which needs an authenticated session. The existing 01 auth doc has register creating PENDING status and sending a verification email rather than tokens, and verify email issues tokens. Either register should issue tokens when email_verified_at is already set or the page should chain through a verify call after register. The cleanest spec is to keep PENDING as the post register status but have register return requires_2fa false plus tokens when the member was created already active, which is a single line in the auth doc.

Second, the wireframe shows opportunity statuses pending vetting approved executing rejected while the existing 04 opportunity doc uses DRAFT SUBMITTED VETTING APPROVED REJECTED EXECUTED and adds EXECUTING as a derived view. Either the wireframe status badges are renamed to the existing enum or the enum in 04 is extended with EXECUTING. The wireframe pages should match the canonical enum from the docs not invent new states.
